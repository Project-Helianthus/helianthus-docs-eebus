# Changelog

## Unreleased

- eeBUS output publication: a consumption-limit write on the EVSE entity is applied through `evse.operation.set_allocated_current`. Amperes are the limit in watts divided by the active phases times the measured phase voltage, rounded down to a whole ampere and clamped from 6 A to the station's configured current; a result below 6 A pauses charging at allocated current 0 A. While any phase carries current, a phase that has carried current since the EV connected keeps counting, so a resuming phase is counted before it resumes. The measured phase voltage is the charging station's phase voltage when that resource publishes one; otherwise it is the measured AC phase voltage of another promoted resource of the same installation, selected by site and electrical relations or, when the installation has exactly one other promoted source, by that source. Several other sources and no selecting relation leave the measured voltage unpublished. A nominal voltage is not used. A limit whose measured voltage, phase current or configured current is not published is answered with a negative acknowledgement that names the missing input. Limitation of Power Consumption V1.0.0 is announced on the EVSE entity when the allocated-current operation is admitted and the host accepts limits; scenarios 1 to 3 are served and scenario 4 is not. Failsafe consumption values are pre-configured to 4200 W and 2 hours. A production-limit write on the Inverter entity stays in watts through `pv.operation.set_active_power_limit`, with no conversion. The page remains a candidate. No contract version is raised; no alias, compatibility shim or migration step is provided.
- Breaking eeBUS library structural JSON name: `usecases` becomes `use_cases` for native, raw and redacted snapshot views. Coordinate consumers in the same wave; no alias, duplicate field, compatibility shim or migration step is provided. Go `UseCases` members and public facade packages remain unchanged. See [the correspondence contract](architecture/naming-contract.md).
- Documentation ownership: the repository README and the architecture overview name the common semantic contract in docs-semantic as the owner of cross-protocol semantics; the docs-ebus shared registry boundary stays the language-neutral registry write boundary and owns no semantic meaning. The native runtime exposure candidate now says that semantic promotion is a separate step that selects what is promoted, and the repository policy validator pins that wording. No alias, compatibility shim or migration step is provided.
- Native relations and participation: the multi-leaf source inventory candidate states, for each bundle, the observed zone-to-room, circuit-to-system-function and setpoint-to-measurement relations with the native field that carries them, or `none_observed`, and declares slot labels local to their bundle, never an identity or an ordinal to join on. The participation contract candidate requires `Selection` to resolve to one element of the common element catalog on one canonical resource and every loss to name its declared target, distinct from plane membership; a selection that names no common element and a loss recorded without a target are rejected. The repository policy validator pins these rules. The registry follow-up in helianthus-eebusreg brings the exported participation contract into line with an in-place edit. No contract version is raised; no alias, compatibility shim or migration step is provided.
- Native SPINE snapshot: a new architecture candidate, `architecture/_candidate/native-snapshot-v2.md`, describes the node kinds, containment relations and their validation rule, the bounded absence records and the identity basis per node kind of the library's native snapshot v2, as native relations rather than common-graph relations. The SKI stays a trust record, never identity. The naming contract gains unchanged rows for the containment, absence and identity-basis keys. Promotion of the page into the stable channel is a later step of the publication procedure. No contract version is raised; no alias, compatibility shim or migration step is provided.
- eeBUS output binding: the candidate `api/_candidate/eebus-output-binding-contract-v1.md` names the input lens `lens.equipment_composition`, composes SPINE entities only from `contains` instances cited in the target's own report, and rejects an entity composed from an index. Features take electrical context only from a cited element, and an operation is admitted only through that resource's own capability; an operation admitted from visibility alone is rejected. Entity addresses persist under the resource identifier alone. Loss and explicit absence are recorded in the same report. The repository policy validator pins these rules. No contract version is raised; no alias, compatibility shim or migration step is provided.
- eeBUS output publication: the candidate `api/_candidate/eebus-output-publication-v1.md` states the 0.7 publication rule. The output is active when the eeBUS runtime is already enabled, and there is no new switch. One advertisement for SHIP stays, with device type EnergyManagementSystem. Lens-admitted inverter, PV string and charger resources are published; a heating resource and a battery resource are not. The node takes the Inverter, PV String and EVSE actors of the cited use cases. It does not announce a use case whose mandatory elements are missing or whose device-side actor is EV. The repository policy validator pins these rules. No contract version is raised; no alias, compatibility shim or migration step is provided.
