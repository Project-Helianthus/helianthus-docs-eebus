## Supported And Unresolved Claims

The inspected source supports an implementation-level claim only. It does not

steps.

## Bounded Live Observation

The reviewed build was deployed on one local runtime with one previously
trusted SHIP peer. Four consecutive start or restart cycles returned to one
paired, connected session without the previously observed collision close,
duplicate-connection diagnostic, terminal state-wait close, panic, or fatal
runtime result.

The final cycle completed a read-only SPINE feature request and returned a
reply from the same connection generation. Durable mutation state remained
empty. Peer identity, protocol addresses, private network details, protocol values,
ephemeral tokens, and binary digests are intentionally not published.

This observation does not cover a second peer, trust establishment, write
behavior, arbitrary timing, packet loss, or complete session-collision
conformance.

## Falsification Criteria

This record is falsified by any final reviewed source or focused test that
demonstrates one of the following:

1. With a trusted remote and simultaneous attempts, the lower-key initiator's
   direction is retained, or both directions become active.
2. With the local identity key higher and an outbound attempt initiating, the inbound
   connection reaches `Run`, initializes data processing, or reaches protocol
   activation instead of being rejected.
3. An inbound connection starts data processing before Hub ownership is
   registered.
4. After shutdown or a competing replacement closes an inbound connection
   before `Run`, a later `Run` starts a read or write pump, or terminal close is
   reported more than once.
